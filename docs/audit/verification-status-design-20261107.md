# 검증 상태 표시 체계 분석과 개선 설계(설계만, 이번 단계 미적용)

- 작성일: 2026-11-07(Phase B 2차). 이번 단계에서는 **79건 상태를 일괄 변경하지 않았고, 화면에 새 상태 표시를 적용하지 않았습니다.**
- 목적: 사용자가 보는 "최종 확인"이 무엇을 보장하는지 분명히 하고, 후속 구현(Phase C 후보)에 필요한 데이터 구조·화면·검사를 설계합니다.

## 1. 현재 구조

| 필드 | 정의(`data/common.js` 최신성 관리) | 화면 표시 |
|---|---|---|
| `verifiedAt` | 공식 자료와 마지막으로 대조한 날 | 카드·제도마다 "YYYY.MM.DD **최종 확인**"(`sourceLine`). 근거 자료 링크와 함께 표시 |
| `sourceUpdatedAt` | 공식 자료 자체의 시행·개정·게시일 | 표시 안 함(점검 도구만 사용) |
| `reviewStatus` | `verified` · `review-needed` · `source-unavailable` | `source-unavailable`일 때만 "원문 게시물을 다시 확인하고 있어요". **`verified`와 `review-needed`는 화면상 구분되지 않음** |
| `status` | 운영 상태 문자열 | "현재 시행 중"이 아니면 배지("신청 전 확인", "시범 운영", "2026 신청 마감") |
| `validUntil` | 공식 기간의 마지막 날 | 지나면 "기간 확인" 안내(`periodPassed`) |
| `reviewBy` | 운영자 재확인일 | 표시 안 함(점검 도구 경고) |

**현재 분포(지역 사업 192건, 2026-11-07, Phase B2 브랜치):**

| 항목 | 분포 |
|---|---|
| `reviewStatus` | verified 186 · review-needed 6 |
| `status` | 현재 시행 중 187 · 신청 전 확인 3 · 시범 운영 1 · 2026 신청 마감 1 |
| 기간 필드 | `validUntil` 40건 · `reviewBy` 42건 |

**독립 검증(PR #29, Phase A 이전 판정)과의 교차:**

| reviewStatus × PR #29 판정 | 건수 |
|---|---:|
| verified × 확인 완료 | 107 |
| verified × 부분 확인 | 74 |
| verified × 내용 불일치 | 4 |
| verified × 종료·구정보 | 1 |
| review-needed × 부분 확인 | 4 |
| review-needed × 확인 완료 | 2 |

`verified` 186건 중 79건(74+4+1)이 독립 검증의 "확인 완료"가 아닙니다.
- 이 중 Phase A·B1·B2에서 문구를 고친 항목은 경기 P04·경남 P13·인천 P03·울산 P06·대구 P08·충남 P01·경북 P08·부산 P06·P07·서울 P03·대구 P07입니다.
- 이 숫자는 **허위 79건이 아니라 "의미 차이"**입니다. 사이트의 `verified`는 "자료를 대조했다"이고, 독립 검증의 "확인 완료"는 "대상·금액·기한·접수처까지 원문으로 모두 대조했다"입니다.

## 2. 문제

1. **"최종 확인"의 보장 범위가 드러나지 않습니다.** 날짜만 보이고, 무엇을 확인했는지(제도 존재 / 신청 조건 / 신청 경로)가 없습니다.
2. **`review-needed`가 화면에 보이지 않습니다.** 사용자는 다시 확인이 필요한 항목도 다른 카드와 똑같이 "최종 확인"으로 봅니다(충남 P03 등).
3. **공식 자료 간 충돌을 표시할 구조가 없습니다.** 지금은 `caution`·`timing` 문장으로만 알립니다(충남 P03 6개월·1년, 경남 P13 10일).
4. **최신성(시간)과 확인 범위(깊이)가 한 필드에 섞여 있습니다.** `verifiedAt`을 갱신하면 깊이와 관계없이 "최근 확인"으로 보입니다.

## 3. 구분해야 할 상태

| 상태 | 뜻 | 판단 근거 | 사용자 표시(안) |
|---|---|---|---|
| ① 제도 존재 확인 | 공식 기관이 운영하는 제도·사업임을 확인 | 공식 누리집·계획·법령 | 표시 안 함(모든 카드의 최소 조건) |
| ② 신청 조건 확인 | 대상·금액·한도·기한·제외 조건을 원문으로 대조 | 계획·약관·고시·신청 안내 | "신청 조건 확인 YYYY.MM.DD" |
| ③ 신청 경로 확인 | 실제 신청 페이지·서식·접수처(전화·메일)에 도달 | 신청 페이지·서식·업무분장 | "신청 경로 확인"(②와 함께) |
| ④ 최신성 재확인 필요 | 기간 경과, 새 학년도 자료 예정, 법령 개정 시행 | `validUntil`·`reviewBy`·법령 시행일 | 배지 "다시 확인 중" + 문구 |
| ⑤ 공식 자료 간 충돌 | 같은 기관 자료끼리 값이 다름 | 근거 2개 이상과 다른 값 | 배지 "기관 확인 필요" + 충돌 내용·확인처 |

## 4. 데이터 설계(후보)

`reviewStatus`는 유지하고(하위 호환), 항목마다 **선택 필드** `checks`를 추가합니다.

```js
checks: {
  exists:   '2026-11-04',            // ① 제도 존재 확인일
  terms:    '2026-11-07',            // ② 신청 조건(대상·금액·기한·제외) 확인일, 없으면 미확인
  route:    '2026-11-07',            // ③ 신청 경로(페이지·서식·접수처) 확인일
  conflict: '6개월(신청 페이지)·1년(기본계획·개정 길라잡이)'  // ⑤ 충돌 요약(있을 때만)
}
```

- **화면 규칙:** `checks`가 있으면 "최종 확인" 대신 확인한 범위를 짧게 보여 줍니다. 예: "2026.11.07 신청 조건·경로 확인 · 근거 자료 1·2". `checks`가 없으면 지금처럼 "최종 확인"입니다(기존 192건 호환).
- `④`는 새 필드 없이 계산합니다(`validUntil` 경과, `reviewBy` 경과, `reviewStatus: review-needed`). `review-needed`는 화면에 **"다시 확인 중"** 배지로 보여 줍니다.
- `⑤`가 있으면 "기관 확인 필요" 배지와 `conflict` 내용·확인처(`contact`)를 상세에 보여 줍니다.

## 5. 적용 순서(후속 구현)

1. **1단계(코드):** `checks` 선택 필드를 읽는 표시 함수를 추가합니다. 없는 항목은 지금과 똑같이 보입니다. `review-needed` 배지를 표시합니다(현재 6건).
2. **2단계(데이터, 근거 확인한 항목부터):** Phase A·B에서 원문 대조를 마친 항목에 `checks`를 채웁니다. 충남 P03·경남 P13에 `conflict`를 넣습니다.
3. **3단계:** PR #29의 "부분 확인" 78건은 원문을 다시 확인한 순서대로 `terms`·`route`를 채웁니다. **일괄 채우기 금지**입니다.
4. **4단계:** "최종 확인" 문구를 "확인한 범위"로 바꾸는 안내를 서비스 안내(FAQ)에 한 줄 둡니다.

## 6. 검사 설계

| 검사 | 목적 |
|---|---|
| `checks.terms`가 있으면 `amount`·`timing`·`eligibility` 중 하나 이상과 그 값을 뒷받침하는 출처(`source`)가 연결돼야 함 | 근거 없는 "조건 확인" 표시 방지 |
| `checks.route`가 있으면 `channels`(apply/guide) 또는 `apply`에 접수처(전화·메일·페이지)가 있어야 함 | 경로 미확인 항목의 과대 표시 방지 |
| `conflict`가 있으면 `reviewStatus`는 `review-needed`이고 `caution` 또는 `timing`에 확인처 안내가 있어야 함 | 충돌을 확정처럼 쓰지 않게 |
| `checks.*` 날짜는 `verifiedAt`보다 늦을 수 없음 | 날짜 일관성 |
| 기존 192건 중 `checks` 없는 항목은 그대로 통과 | 하위 호환. 개수 고정 검사 금지 |
